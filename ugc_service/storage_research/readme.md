# Исследование хранилищ данных: MongoDB vs PostgreSQL

## 📋 Описание проекта

Данное исследование посвящено выбору оптимального хранилища данных для системы, работающей с фильмами, пользовательскими лайками, рецензиями, закладками и неструктурированными данными.

**Цель:** Определить, какая СУБД (MongoDB или PostgreSQL) лучше справляется с поставленными задачами при соблюдении SLA < 200 мс на все операции.

## 🎯 Требования к системе

### Функциональные требования
- Хранение лайков пользователей к фильмам
- Хранение рецензий с метаданными (текст, дата, автор, лайки/дизлайки, оценки)
- Пользовательские закладки с неструктурированными вложениями
- Логирование пользовательских кликов и истории действий
- Профили пользователей с гибкими настройками
- Дополнительные неструктурированные данные с JSON-подобными документами

### Нефункциональные требования
- **SLA:** Все операции чтения/записи должны выполняться за **< 200 мс**
- **Объем данных:** 10 миллионов записей
- **Неструктурированные данные:** 500,000 документов со случайной структурой

## 🏗️ Архитектурное решение

### Выбор хранилища: **MongoDB**

**Обоснование:**
1. **Природа данных:** 80% данных являются неструктурированными или полуструктурированными (профили, закладки, логи, события)
2. **Гибкость схемы:** MongoDB позволяет хранить документы с разной структурой без миграций
3. **Производительность:** Нативная работа с вложенными JSON-документами, dot notation для запросов
4. **Масштабируемость:** Горизонтальное масштабирование через шардирование

**Почему не PostgreSQL?**
- Требует использования `jsonb` для неструктурированных данных
- Сложные запросы с операторами `->`, `->>`, `@>`
- GIN-индексы эффективны только для определенных операций
- Миграции при изменении структуры данных

### Модель данных

**MongoDB Collections:**
- `users` — профили с вложенными настройками и закладками
- `movies` — фильмы с преагрегированными счетчиками лайков и рейтинга
- `user_likes` — лайки пользователей
- `action_logs` — логи действий
- `unstructured_events` — неструктурированные события со случайной структурой

**Ключевая оптимизация:** Преагрегация счетчиков (лайков, рейтинга) в документе фильма для исключения тяжелых `COUNT` и `AVG` операций на чтение.

### Архитектура сервиса

**Рекомендация:** Разработка **отдельного микросервиса** для работы с лайками, логами и профилями.

**Преимущества:**
- Независимое масштабирование под разные паттерны нагрузки
- Изоляция сбоев (падение сервиса логов не влияет на основной функционал)
- Свобода выбора стека технологий

**Проблемы:**
- Сетевые задержки между сервисами
- Сложность распределенных транзакций (решается через eventual consistency)

### Анализ по категориям

#### 1. Структурированные данные (лайки, закладки)
- **MongoDB:** 1.37 - 1.99 мс
- **PostgreSQL:** 1.79 - 2.97 мс
- **Вывод:** MongoDB быстрее на 20-33% благодаря документоориентированной модели

#### 2. Операции записи
- **MongoDB:** 4.11 мс (Write Like + Read)
- **PostgreSQL:** 10.59 мс
- **Вывод:** MongoDB в **2.5 раза быстрее** на операциях записи с чтением

#### 3. Неструктурированные данные
- **Insert:** MongoDB (1.43 мс) vs PostgreSQL (5.62 мс) — **в 4 раза быстрее**
- **Read by ID:** MongoDB (1.31 мс) vs PostgreSQL (1.58 мс) — на 17% быстрее
- **Query nested:** MongoDB (1.47 мс) vs PostgreSQL (1.91 мс) — на 23% быстрее
- **Вывод:** MongoDB значительно эффективнее работает с неструктурированными данными

## ✅ Соответствие SLA

**Обе базы данных укладываются в требование < 200 мс:**

- **MongoDB:** Максимальное время — 4.11 мс (Write Like + Read Count)
- **PostgreSQL:** Максимальное время — 10.59 мс (Write Like + Read Count)

**Запас по SLA:**
- MongoDB: **48x** (200 / 4.11)
- PostgreSQL: **19x** (200 / 10.59)

## 🎯 Выводы

### 1. Производительность
**MongoDB показала лучшие результаты во всех сценариях:**
- В среднем на **30-40% быстрее** на операциях чтения
- В **2-4 раза быстрее** на операциях записи
- Особенно эффективна на неструктурированных данных

### 2. Соответствие требованиям
Обе СУБД удовлетворяют SLA < 200 мс, но MongoDB имеет больший запас производительности.

### 3. Архитектурные преимущества MongoDB
- Нативная поддержка JSON-документов
- Гибкая схема без миграций
- Простые запросы к вложенным полям (dot notation)
- Лучшая производительность на неструктурированных данных

### 4. Рекомендации

**Для данного проекта рекомендуется MongoDB** по следующим причинам:
1. 80% данных — неструктурированные или полуструктурированные
2. Требуются частые изменения схемы (профили, закладки)
3. Высокая нагрузка на запись (логи, лайки)
4. Необходимость быстрого чтения вложенных данных

**Альтернативный сценарий:** Если бы данные были строго структурированными (например, финансовая система с транзакциями), PostgreSQL был бы предпочтительнее благодаря ACID-транзакциям и строгой схеме.

