

# 1. Функциональные требования (Functional Requirements)

Функциональные требования описывают, **что** система должна делать. Они разбиты на логические модули (эпики).

### Модуль 1: Управление профилем пользователя (CRUD)
*   **FR1.1. Создание профиля (Create):** Система должна позволять пользователю зарегистрироваться и создать профиль, указав ФИО и номер телефона.
*   **FR1.2. Согласие на обработку ПДн и маркетинг:** При создании/редактировании профиля система должна предоставлять чекбоксы (согласия) на:
    *   Обработку ПДн (обязательно).
    *   Получение маркетинговых рассылок (SMS/звонки) на указанный номер (опционально, по умолчанию выключено).
    > Исключено в связи с избыточностью в учебном проекте.
*   **FR1.3. Чтение профиля (Read):** Пользователь должен иметь возможность просматривать данные своего профиля.
*   **FR1.4. Обновление профиля (Update):** Пользователь должен иметь возможность изменять свои ФИО и номер телефона. При изменении номера телефона система должна требовать его повторного подтверждения (через SMS-код).
    > Подтверждение через SMS-код исключено в связи с избыточностью в учебном проекте — номер обновляется без верификации.
*   **FR1.5. Удаление профиля (Delete):** Пользователь должен иметь возможность полностью удалить свой профиль и все связанные данные (право на забвение / отзыв согласия на обработку ПДн).

### Модуль 2: Двухфакторная авторизация (2FA)
> Исключено в связи с избыточностью в учебном проекте.
*   **FR2.1.** Система должна поддерживать вход в аккаунт с использованием логина/пароля и подтверждения через SMS-код, отправляемый на привязанный номер телефона.
*   **FR2.2.** Система должна позволять пользователю включать/отключать 2FA в настройках профиля.

### Модуль 3: Избранное (Понравившиеся фильмы)
*   **FR3.1.** Пользователь должен иметь возможность добавлять фильмы в список «Избранное».
*   **FR3.2.** Пользователь должен иметь возможность удалять фильмы из «Избранного».
*   **FR3.3.** Пользователь должен иметь возможность просматривать список своих избранных фильмов с возможностью пагинации и сортировки (по дате добавления, названию).

### Модуль 4: Рейтинги и Рецензии
*   **FR4.1. Выставление оценки:** Пользователь должен иметь возможность поставить фильму оценку по шкале от 1 до 10 (целое число).
    > Оставляем как есть — 0–10, соответствует текущей реализации `ugc_service`, без изменений.
*   **FR4.2. Изменение/удаление оценки:** Пользователь может изменить или удалить свою оценку.
*   **FR4.3. Написание рецензии:** Пользователь должен иметь возможность написать текстовую рецензию на фильм (заголовок + текст).
*   **FR4.4. Модерация рецензий (опционально, но рекомендуется):** Система должна позволять помечать рецензию как «Спойлер» (скрывать текст под катом).
*   **FR4.5. Редактирование рецензии:** Пользователь может редактировать или удалять свои рецензии.

### Модуль 5: Просмотр данных о фильме (Публичная часть)
*   **FR5.1.** На странице фильма система должна отображать **средний рейтинг** (на основе оценок пользователей) и **общее количество оценок**.
*   **FR5.2.** На странице фильма система должна отображать список **рецензий пользователей** (с пагинацией, сортировкой по дате, полезности или рейтингу).
*   **FR5.3.** Пользователь должен видеть, поставил ли он уже оценку или написал рецензию на данный фильм.

### Модуль 6: Административная панель
*   **FR6.1. Доступ по ролям (RBAC):** Просмотр профилей должен быть доступен только пользователям с ролью «Администратор» или «Модератор».
*   **FR6.2. Поиск и фильтрация:** Администратор должен иметь возможность искать профили по ФИО, номеру телефона или ID пользователя.
*   **FR6.3. Просмотр деталей:** Администратор должен видеть полную карточку пользователя (ФИО, телефон, статус маркетинга, дата создания, список избранных фильмов, последние рецензии).
    > Статус маркетингового согласия не показываем — согласие (FR1.2) исключено из проекта, пункт не актуален.
*   **FR6.4. Аудит действий:** Система должна логировать факт просмотра администратором карточки пользователя (кто, когда, чей профиль смотрел).

# 2. Нефункциональные требования (Non-Functional Requirements)

Нефункциональные требования описывают, **как** система должна работать (безопасность, производительность, надежность).

### Безопасность и Приватность (Критично из-за ПДн)
*   **NFR1. Шифрование данных (Data at Rest):** Номера телефонов и ФИО в базе данных должны храниться в зашифрованном виде (например, с использованием AES-256). Ключи шифрования должны храниться в отдельном защищенном хранилище (KMS).
    > Исключено в связи с избыточностью в учебном проекте.
*   **NFR2. Шифрование трафика (Data in Transit):** Все взаимодействие с API должно происходить по протоколу HTTPS (TLS 1.2/1.3).
*   **NFR3. Маскирование в логах:** Номера телефонов и ФИО **ни в коем случае** не должны попадать в логи приложения в открытом виде (должны маскироваться, например: `+7 *** *** ** 45`).
    > Исключено в связи с избыточностью в учебном проекте.
*   **NFR4. Разделение баз данных (или схем):** Данные профилей (ПДн) рекомендуется хранить в отдельной БД или изолированной схеме от данных рейтингов и рецензий, чтобы минимизировать риски утечки.
*   **NFR5. Защита от перебора (Brute-force):** Ограничение количества попыток ввода SMS-кода для 2FA (не более 3-5 попыток с последующей блокировкой на N минут).
    > Исключено в связи с избыточностью в учебном проекте (зависит от Модуля 2, тоже исключённого).

### Производительность и Масштабируемость
*   **NFR6. Время отклика API:** 95% запросов на чтение профиля, добавление в избранное и выставление оценки должны выполняться не более чем за 200 мс.
*   **NFR7. Кэширование агрегированных данных:** Средний рейтинг фильма и количество рецензий должны кэшироваться (например, в Redis) и пересчитываться асинхронно, чтобы избежать тяжелых `JOIN` и `AVG` запросов к БД при каждом открытии страницы фильма.
*   **NFR8. Масштабируемость чтения:** Страница фильма (где выводятся рецензии и рейтинг) должна выдерживать высокие нагрузки на чтение (Read-heavy).

### Надежность и Доступность
*   **NFR9. SLA:** Доступность сервиса профилей и API оценок — 99.9% в месяц.
*   **NFR10. Резервное копирование:** Ежедневное создание бэкапов БД с ПДн с хранением в зашифрованном виде в течение 30 дней.

### UX / UI и Валидация
*   **NFR11. Валидация телефона:** Система должна принимать номер телефона строго в международном формате (E.164) и проверять его существование/валидность перед отправкой SMS.
    > Проверка существования номера перед отправкой SMS исключена в связи с избыточностью в учебном проекте (SMS не используется). Формат E.164 проверяем как обычную валидацию ввода.
*   **NFR12. Защита от спама в рецензиях:** Ограничение на частоту написания рецензий (например, не более 10 рецензий в час) и внедрение капчи/anti-fraud систем при подозрительной активности.
*   **NFR13. Адаптивность:** API должно быть спроектировано так, чтобы поддерживать как Web-интерфейс, так и мобильные приложения (iOS/Android).

# 3. Вопросы и Риски для Бизнеса (Must Have для Системного Аналитика)

> Раздел носит информационный характер — риски пока не прорабатываются в рамках учебного проекта.

Перед началом разработки есть несколько дополнительных вопросов, так как в ТЗ есть «подводные камни»:

1.  **Юридические риски (Маркетинг):** Использование номера телефона для маркетинга требует явного, информированного, конкретного и сознательного согласия пользователя (согласно 152-ФЗ в РФ или GDPR в Европе). *Решение:* Сделать отдельный чекбокс «Согласен получать рекламные SMS/звонки». Передавать номер маркетологам можно **только** если эта галочка стоит.
2.  **Риски хранения ПДн:** Хранение ФИО и Телефонов в одном сервисе с отзывами и рейтингами создает риск. Если сервис отзывов взломают, злоумышленники получат базу ПДн. *Решение:* Разделить микросервисы. Сервис «Профили и ПДн» должен быть закрыт от публичного доступа и общаться с сервисом «Отзывы/Рейтинги» только по внутреннему защищенному контуру, передавая только `user_id`, но не ФИО/Телефон.
3.  **Уникальность пользователя:** Бизнес хочет использовать телефон для «определения уникальности». Но телефоны могут меняться, использоваться несколькими членами семьи или быть виртуальными. *Решение:* Телефон — это хороший идентификатор, но для уникальности лучше использовать связку `user_id` (внутренний UUID) + `device_id` (для антифрода).
4.  **Модерация отзывов:** Где гарантия, что пользователи не будут писать оскорбления или спойлеры? *Решение:* Заложить в бэклог функционал «Пожаловаться на отзыв» и очередь модерации для админов.
5.  **Стоимость SMS:** Если телефон используется для 2FA и маркетинга, бизнес должен заложить бюджет на SMS-шлюз. *Решение:* Предложить бизнесу альтернативу для 2FA — push-уведомления в приложение или код в мессенджер (WhatsApp/Telegram Bot), это дешевле и надежнее.
