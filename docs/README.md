## 1. Функциональные требования.

### 1.1. Отслеживание кликов.

FR- 1 : Сервис должен регистрировать события кликов по ключевым элементам интерфейса.  
FR- 2 : Для события клика должны собираться атрибуты элемента.  
FR- 3 : Должен поддерживаться сбор кликов в разных зонах сайта.  

### 1.2. Отслеживание просмотров страниц.
FR- 5 : Сервис должен регистрировать события открытия страницы.  
FR- 6 : Сервис должен регистрировать события завершения просмотра страницы или потери фокуса.  
FR- 7 : Для каждой страницы должны собираться тип и идентификатор.  
FR- 8 : Сервис должен собирать длительность нахождения пользователя на странице.  
FR- 9 : Нужно корректно обрабатывать SPA-навигацию.  
FR-10 : Учитывать активность вкладки.  

### 1.3. Отслеживание кастомных событий.
#### 1.3.1. Смена качества видео.
FR-11 : Сервис должен фиксировать каждое изменение качества видео.  
FR-12 : Событие должно содержать предыдущее и новое качество.  
FR-13 : Событие должно быть привязано к контенту и сессии просмотра.  

#### 1.3.2. Просмотр видео до конца.
FR-14 : Сервис должен фиксировать просмотр фильма или шоу до конца.  
FR-15 : Нужно определять критерий “просмотр до конца”.  
FR-16 : Событие должно содержать данные о контенте и прогрессе.  

#### 1.3.3. Использование фильтров поиска.
FR-17 : Сервис должен фиксировать применение пользователем фильтров поиска.  
FR-18 : Для события фильтра нужно указывать тип фильтра и значение.  
FR-19 : Желательно связывать событие фильтра с поисковым запросом или сессией поиска.  
FR-20 : Можно фиксировать результат поиска.  

### 1.4. Общие функциональные требования к сбору и отправке событий.
FR-21 : Должен быть клиентский SDK или JavaScript-модуль для сбора событий.  
FR-22 : Должен быть API для приема событий.  
FR-23 : Каждое событие должно иметь уникальный идентификатор.  
FR-24 : Каждое событие должно содержать временную метку.  
FR-25 : События должны содержать идентификатор пользователя и/или анонимный идентификатор.  
FR-26 : События должны содержать идентификатор сессии.  
FR-27 : Сервис должен валидировать входящие события.  
FR-28 : Сервис должен поддерживать дедупликацию событий.  
FR-29 : Сервис должен поддерживать повторную отправку событий клиентом.  
FR-30 : Должна быть возможность добавлять новые типы событий.  
FR-31 : События должны сохраняться для дальнейшего анализа.  
FR-32 : Должен быть механизм выгрузки или доступа к собранным данным.  
FR-33 : Должна учитываться настройка согласия пользователя.  

## 2. Нефункциональные требования.
### 2.1. Производительность и пропускная способность.  
NFR- 1 : Сервис должен обрабатывать целевую нагрузку без деградации сайта.  
NFR- 2 : Endpoint приема событий должен отвечать быстро (p99.9 latency ≤ 500 мс).  
NFR- 3 : Отправка аналитики не должна блокировать интерфейс пользователя.  
NFR- 4 : Клиентский SDK должен иметь минимальное влияние на загрузку страницы.  
NFR- 5 : Сервис должен поддерживать пакетную отправку событий.  

### 2.2. Доступность и надежность.
NFR- 6 : Сервис сбора событий должен быть высокодоступным(доступность ≥ 99.9% в месяц.)  
NFR- 7 : Потеря событий после успешного подтверждения должна быть минимальной (durability принятых событий ≥ 99.99% или использование реплицированной очереди/хранилища).  
NFR- 8 : Сервис должен переживать сбои без потери данных от клиента (Клиентская очередь, повторные попытки, серверная очередь, dead-letter queue).  
NFR- 9 : Должна быть защита от лавинных ретраев (Экспоненциальная задержка повторных отправок, jitter, circuit breaker).  
NFR-10 : Должна быть обработка пиковых нагрузок (RPS=800).  

### 2.3. Масштабируемость.
NFR-11 : Сервис должен масштабироваться горизонтально.  
NFR-12 : Хранилище должно масштабироваться под рост объема событий.  
NFR-13 : Архитектура должна позволять увеличивать количество событий без переписывания системы.  

### 2.4. Целостность и качество данных.
NFR-14 : Должна быть защита от дублей.  
NFR-15 : Допускается eventual consistency для аналитических данных.  
NFR-16 : События должны быть упорядочены хотя бы в рамках сессии.  
NFR-17 : Нужно учитывать поздно доставленные события.  
NFR-18 : Должна быть возможность отбрасывать или помечать некорректные события.  

### 2.5. Безопасность и приватность.
NFR-19 : Передача событий должна идти по HTTPS (TLS 1.2+).  
NFR-20 : Должна быть авторизация клиентской части.  
NFR-21 : Нужно ограничивать частоту запросов (Rate limiting для защиты).  
NFR-22 : В событиях не должно быть лишних персональных данных (Минимизация PII: не отправлять email, телефон, пароль и т.п.).  
NFR-23 : Нужно учитывать требования согласия пользователя (Opt-in/opt-out, cookie consent, возможность не собирать идентифицирующие данные).  
NFR-24 : Должна поддерживаться анонимизация или псевдонимизация (Особенно если сервис работает с неавторизованными пользователями).  

### 2.6. Расширяемость и поддерживаемость.
NFR-25 : Схема событий должна поддерживать версионирование.  
NFR-26 : Должна быть возможность добавлять новые кастомные события.  
NFR-27 : Сервис должен быть наблюдаемым.  
NFR-28 : Должно быть логирование и трассировка.  
NFR-29 : Должна быть документация по формату событий.  

### 2.7. Требования к хранению.
NFR-30 : Нужно определить срок хранения сырых событий (30–90 дней в горячем хранилище, далее в архиве 180 дней).  
NFR-31 : Данные должны быть пригодны для ретроспективного анализа.  
NFR-32 : Должна быть возможность агрегировать данные.  

## 3. Предполагаемые метрики нагрузки.

### 3.1. Базовые допущения.
Предположим, что сервис используется как сайт/видеосервис среднего масштаба.  

| Метрика | Значение | Комментарий |
|  ---    |  ---:    |    ---      |
| MAU | 5 000 000 | Уникальные активные пользователи за месяц. |
| DAU | 500 000 | Примерно 10% от MAU. |
| Среднее число сессий на DAU | 1.5 | Пользователь может заходить несколько раз в день. |
| Среднее число page views на пользователя в день | 7 | Просмотры главной, фильма, категории, поиска. |
| Среднее число кликов на пользователя в день | 10 | Клики по карточкам, категориям, трейлерам, баннерам. |
| Среднее число кастомных событий на пользователя в день | 3 | Смена качества, досмотры, фильтры поиска. |
| Итого событий на DAU в день | 20 | 7 + 10 + 3. |
| Средний размер одного события | ~1 КБ | Небольшой JSON с контекстом. Реалистичный диапазон: 0.7–1.5 КБ. |

### 3.2. Расчет количества событий в день
Формула:  
Daily Events = DAU × Events per user per day  
Для базового сценария:  
Daily Events = 500 000 × 20 = 10 000 000 событий в день  

### 3.3. Средний RPS
Формула:  
Average RPS = Daily Events / 86 400  
Где 86 400 — количество секунд в сутках.  
Average RPS = 10 000 000 / 86 400 ≈ 116 событий в секунду.  

То есть в среднем сервис должен принимать около **116 событий в секунду**.

### 3.4. Пиковый RPS
Для веб-сервисов обычно нужно учитывать пиковые нагрузки: вечер, выходные, премьеры, маркетинговые акции.  
Возьмем коэффициент пика: Peak Factor = 4  

Тогда:  
Peak RPS = 116 × 4 ≈ 464 события в секунду  

С учетом запаса на ретраи, ботов, некорректные события и будущий рост рекомендуется проектировать сервис на:  
Target RPS ≈ 800 событий в секунду

Если предполагается более активное использование heartbeat-событий для измерения времени на странице, нагрузку нужно увеличить.  
Например, если добавляется 15–30 heartbeat-событий на пользователя в день, то:  

Events per user per day = 20 + 30 = 50  
Daily Events = 500 000 × 50 = 25 000 000  
Average RPS ≈ 289  
Peak RPS ≈ 1156  
Target RPS ≈ 2000  

Поэтому важно отдельно зафиксировать способ измерения времени на странице.  

### 3.5. RPS HTTP-запросов при пакетной отправке
Если клиент отправляет события не по одному, а батчами, то HTTP RPS будет ниже.

Например, batch size = 10 событий:

Average HTTP RPS = 116 / 10 ≈ 12
Peak HTTP RPS = 464 / 10 ≈ 46
Target HTTP RPS = 80

Однако при проектировании лучше оперировать именно событийной нагрузкой: **event RPS**, а не только HTTP request RPS.

### 3.6. Размер среднего сообщения
Cостав одного события:

| Метрика | Значение |
|  ---    |    ---   |
| Общие поля: event_id, event_type, timestamp, user_id, session_id | 200–300 байт |
| Контекст: страница, устройство, браузер, версия приложения | 200–400 байт |
| Полезная нагрузка события | 200–500 байт |
| JSON-синтаксис и служебные поля | 100–200 байт |

Итого: Средний размер события ≈ 0.7 – 1.5 КБ  

Для расчетов удобно использовать:  
Average message size = 1 КБ  

Для батча из 10 событий:  
Batch size ≈ 10 КБ  
С учетом сжатия gzip/br фактический сетевой размер может быть в 2–5 раз меньше.  

### 3.7. Объем данных в день
Формула:  
Daily Data Volume = Daily Events × Average message size  

Для базового сценария:  
Daily Data Volume = 10 000 000 × 1 КБ ≈ 10 ГБ в день  

В месяц:  
Monthly Data Volume ≈ 10 ГБ × 30 = 300 ГБ в месяц  

Это объем сырых событий без учета сжатия, дедупликации и колоночного хранения. После сжатия и оптимизации объем может быть значительно меньше.
